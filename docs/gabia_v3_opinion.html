수정 제안 영상 트래픽 대책은 "0으로 만든다" 가 아니라 줄인다 입니다.

  1. 재생용은 720p 트랜스코딩본을 따로 두고 원본은 다운로드 전용 (측정: 1080p 90초 = 17.9MB → 720p 90초 ≈ 8~9MB)
  2. 자주 보는 영상은 로컬 캐시에 미리 채움 (이미 _media_cache 존재)
  3. 월 전송량 한도를 서버 계약에서 반드시 확인 (항목 1)

300개 전량 코덱 조사는 별도 작업으로 분리합니다.

7/readyz 설계 — _load_json 확인 후

먼저 _load_json 을 읽었습니다 (proxy_server.py:4727)

확인 사실 · 동작 순서

  1. _JSON_CACHE 에 있고 신선하면 → 즉시 반환
  2. 신선하지 않지만 age < ttl + 여유 → 묵은 값을 먼저 반환하고 _json_refresh_bg 로 백그라운드 갱신
  3. 그 외 → _mirror_read() 를 먼저 시도 (로컬 미러)
  4. 미러도 없으면 NAS.exists() → NAS.read()
  5. 성공하면 _accept() 가 캐시 + 미러에 기록
  6. 예외가 나면 절대 raise 하지 않습니다. 캐시본이 있으면 그걸, 없으면 default 반환
  7. _is_empty_list 가드 — 비어 있지 않은 기존 값을 빈 리스트로 덮어쓰지 못하게 막음
이것이 /readyz 설계에 주는 제약 _load_json 은 실패해도 성공처럼 보입니다. NAS 가 죽어도 default 를 돌려주므로 호출부는 알 수 없습니다. → "데이터를 읽었다" 를 readiness 신호로 쓸 수 없습니다. 미러가 살아 있으면 NAS 가 죽어도 정상 응답합니다(설계 의도).

9공개/비공개 캐시 정책 분리

정정 — 비공개 사진에 public·immutable 을 붙이고 있었습니다 _img_bytes() (proxy_server.py:18284) 는 tier 만 보고 정책을 정합니다. 사진이 공개인지 비공개인지 전혀 구분하지 않습니다. 
max_age = 2592000 if tier in ("thumb", "mid") else 86400
cc = "public, max-age=%d" % max_age
if tier in ("thumb", "mid"):
    cc += ", immutable"

반면 _photo_view_allowed() (:17924) 는 이렇게 못박고 있습니다.

"※ 사진은 '공개 자료'가 아니다."
"번호를 1씩 올려 전 회원 얼굴을 무단 수집하는 것만 막는다."

→ 접근은 막으면서 응답 헤더로는 공개 캐시 가능이라고 알려주고 있었습니다. 일관성이 깨진 상태입니다. 지적이 정확합니다.

무엇이 위험한가

지시자의미와 위험
public공유 캐시(프록시·CDN)가 저장해도 된다는 뜻. Gabia 앞단에 캐시가 있으면 회원 사진이 그 캐시에 남을 수 있음
immutable최대 30일 동안 재검증 없이 그 사본을 쓴다는 뜻. 사진을 삭제·교체해도 최대 30일간 옛 사본이 보일 수 있음
결과no-store 를 붙이던 _cors() 의 보안 의도(F02, 개인정보 캐시 금지)를 _img_bytes 가 정면으로 뒤집고 있음

정정 — "재방문 트래픽 0" 은 성립하지 않습니다

확인 사실

  • max-age 는 브라우저가 그렇게 하기로 약속하는 것이지 서버가 트래픽을 보장하는 것이 아님
  • 캐시를 지우면, 다른 브라우저·기기면, 시크릿 모드면 다시 받습니다
  • Vary: Origin 이 붙어 있어 출처가 다르면 캐시가 분리됨
  • → 정확한 표현은 "재방문 시 브라우저 캐시를 쓸 가능성이 높다". "0"·"보장" 은 철회합니다.

CORS 제한과 서버 인증은 별개입니다 — 지적 수용

확인 사실 CORS 는 브라우저가 다른 출처의 JS 에 응답을 읽히지 않게 막는 장치입니다. 서버 간 접근, curl, <img> 태그는 CORS 로 막히지 않습니다. 따라서 "CORS 를 걸었으니 사진이 보호된다" 는 성립하지 않습니다. 실제 보호는 _photo_view_allowed() 의 세션 검사입니다. 제 v2 는 이 둘을 섞어 서술했습니다 — 분리합니다.

  • endswith 비교라서 https://evil-tsak.kr 같은 문자열은 https://tsak.kr 로 끝나지 않으므로 통과하지는 않습니다. 다만
  • .sandbox.novita.ai 는 모든 샌드박스 출처를 허용하므로 운영 전 반드시 제거해야 합니다
  • CSV 장부 내보내기(:20844)는 Access-Control-Allow-Origin: * 를 직접 붙입니다. 인증은 걸려 있지만 헤더는 전역 허용 — 정리 대상

수정 제안 ① .sandbox.novita.ai 제거(운영 배포 시) ② CSV 의 * 제거 → 동일 출처만 ③ origin.endswith(a) → origin == a 로 엄격화. 위 3개는 코드 수정이므로 별도 승인 후 진행.

10로컬 데이터의 영구/캐시 분류

확인 사실 지적 수용 — 디렉터리가 있다는 사실만으로 용량이 두 배가 되지 않습니다. 실제로 두 배가 되는 것은 같은 내용이 양쪽에 실제로 쓰였을 때입니다. v2 는 이 구분 없이 서술했습니다.

실제로 중복이 확인된 항목만

  • .static_compress_cache 1.1GB — Flutter 정적 자산(41MB)의 gzip 사본. 원본이 STATIC_DIR 에 있으므로 완전 중복. 재생성 가능
  • .thumb_cache 127MB — NAS .thumbnails 의 사본. 중복. 재생성 가능
  • .media_cache 110MB — NAS 영상/미디어의 사본. 중복. 재생성 가능
  • gdrive_store 3.0GB — 백엔드가 gdrive 모드일 때의 원본 보관소. 현재 백엔드는 NAS 이므로 읽기 캐시로 동작. ⚠️ 영구인지 캐시인지 확인 필요
  • .safe_snapshots 334MB — 저장 직전 JSON 회전 백업. 유일본에 가까움. 재생성 불가. 캐시로 취급하면 안 됨

11NAS 5001 인터넷 공개를 전제하지 않기

확인 사실 현 구성은 nas.base = https://39.123.241.4:5001 입니다. 프록시 서버가 이 주소로 직접 접속합니다. 여기서 파생되는 사실:

  • 이 프록시가 도는 곳에서 5001 이 도달 가능해야 NAS 가 동작
  • 샌드박스(외부 클라우드)에서 도달한다는 것은 5001 이 인터넷에 열려 있다는 뜻 (실측: NAS 읽기·쓰기 모두 성공)
  • 즉 현재 구조는 NAS 5001 공개를 사실상 전제하고 있습니다. 보안상 바람직하지 않습니다
  • 운영 서버가 가비아로 가면 "가비아 서버 IP 만 5001 허용" 으로 좁힐 수는 있으나, 그것도 5001 을 여전히 인터넷에 노출하는 구성입니다

이 구조에서 지켜지는 것

브라우저에 NAS 관리자 계정·세션은 노출되지 않습니다 브라우저는 프록시의 API 만 호출하고, 프록시가 서버 측에서 NAS 에 로그인합니다. 쿠키는 프록시 프로세스 메모리에만 있습니다. 이 부분은 지적하신 우려와 달리 현재도 지켜지고 있습니다. 브라우저로 나가는 쿠키는 tsak_sid(HttpOnly, SameSite=Strict) 뿐입니다.
단, 항목 5 의 문제가 더 급합니다 앱 비밀번호 = NAS 비밀번호, 그리고 그것이 JS 번들에 평문으로 있습니다. "세션은 노출되지 않는다" 와 "비밀번호가 노출되었다" 는 별개 문제이며 후자가 더 급합니다.

12JSON 저장소 원자성·동시성·백업

① _save_json 은 원자적이지 않습니다

확인 사실 동작 순서:

  1. _json_gen_bump(path) — 세대 증가 (경쟁 창 닫기 목적)
  2. _guard_destructive_save() — 파괴적 저장이면 False 반환하고 중단
  3. _safe_snapshot(path) — 회전 백업 (실패해도 계속)
  4. NAS.write(path, json.dumps(…)) — NAS 에 통째로 덮어쓰기
  5. _JSON_CACHE[path] = (obj, time.time()) — 캐시 갱신
  6. _lpi_invalidate, _mirror_write()
원자성이 없는 지점 4번이 nas_lib.write() 입니다. 이 함수는 SYNO.FileStation.Upload 에 overwrite: true 로 파일을 직접 덮어씁니다. 임시 파일에 쓰고 rename 하는 절차가 없습니다. → 쓰기 도중 실패하면 파일이 반쯤 쓰인 상태로 남을 수 있습니다. 로컬 미러도 같은 방식입니다.

② 실패 반환이 무시됩니다

"⚠️ 차단되면 False 를 돌려준다. 호출부 103곳이 반환값을 무시하므로, 차단 사실이 조용히 묻히지 않도록 아래에서 전역 카운터에 남긴다." — 코드 주석 인용

→ _guard_destructive_save 가 저장을 막아도 호출부는 성공으로 믿습니다. 관측 수단은 /api/health 의 saveGuard.blockedCount 뿐입니다. 실측: 현재 blockedCount = 0.

③ 전역 쓰기 락이 없습니다

존재하는 락: LOCK, _SESS_LOCK, _ACCESS_LOG_LOCK, _BOARD_WRITE_LOCK, _REVIEW_WRITE_LOCK, _IPWATCH_LOCK, _MEMBER_WRITE_LOCK, _HISTORY_LOCK → _save_json 전체를 감싸는 락은 없습니다. 게시판·후기·회원은 개별 락이 있으나 그 외 JSON 은 무방비입니다.
