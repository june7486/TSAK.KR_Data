 항목 2 — Python 버전과 Pillow wheel (정정)
════════════════════════════════════════════════════════════════════

■ 정정 1: Pillow 9.5.0 cp39 wheel 은 존재합니다

[확인 사실 — 실측]
  PyPI JSON API 로 직접 조회한 결과, Pillow 9.5.0 에는 아래 wheel 이 있습니다.
    Pillow-9.5.0-cp39-cp39-manylinux_2_17_x86_64.manylinux2014_x86_64.whl
    Pillow-9.5.0-cp39-cp39-manylinux_2_28_x86_64.whl
  즉 "9.5.0 은 cp39 wheel 이 없어서 못 쓴다"는 제 이전 서술은 **거짓**입니다.
  지적이 정확했습니다.

  참고로 함께 확인한 사실:
    · Pillow 10.4.0, 11.3.0 에도 cp39 Linux x86_64 wheel 존재
    · Pillow 12.x 대에는 cp39 wheel 없음 (cp310 이상)

  제가 앞서 "9.5.0 은 불가, 11.3.0 이 상한" 이라고 쓴 것은 잘못된 측정
  (대소문자 구분 ls, 실패한 grep 패턴)에서 나온 오판이었습니다.

■ 정정 2: Python 3.9 는 이미 지원 종료입니다

[확인 사실 — 실측, 기준일 2026-11-20]
    Python 3.9   지원 종료 2025-10-31  → 이미 종료
    Python 3.10  지원 종료 2026-10-01  → 이미 종료
    Python 3.11  지원 종료 2027-10-31  → 보안 지원 중
    Python 3.12  지원 종료 2028-10-31  → 보안 지원 중
    Python 3.13  지원 종료 2029-10-31  → 보안 지원 중
  따라서 **최소 3.11 이상**에서 검토해야 합니다.
  "Pillow 9.5.0 이 cp39 wheel 을 가지므로 3.9 를 쓰자"는 논리는
  wheel 존재와 무관하게 성립하지 않습니다. 3.9 자체가 EOL 이기 때문입니다.

■ wheel 존재와 앱 실행 검증은 다릅니다

[확인 사실]
  · wheel 이 있다 = 설치가 된다. 여기까지입니다.
  · 설치가 된다 ≠ 앱이 동작한다.

[확인 사실 — 코드에서 확인한 3.12+ 제거 API 미사용]
  img_pipeline.py 를 확인한 결과, Python 3.12 에서 제거된 API 를 쓰지 않습니다.
    · `Image.ANTIALIAS` 미사용 → `Image.LANCZOS` 사용 (정상)
    · `ImageDraw.textsize()` 미사용
    · `im.thumbnail((side, side), Image.LANCZOS)` — 현행 API
    · `im.save(buf, "WEBP", quality=..., method=6)` — 현행 API
  PyMuPDF / openpyxl 은 이 파이프라인에서 이미지 처리 경로에 쓰이지 않습니다.

[수정 제안]
  · 운영 Python 은 **3.12 권장, 최소 3.11** 로 표기합니다.
  · 버전 확정 시 아래 3개만 실제로 실행해 검증합니다.
      ① `pip install Pillow PyMuPDF openpyxl` 이 오류 없이 완료되는가
      ② `img_pipeline.make_all()` 이 실제 사진 1장에 대해
         (bytes, ext, mime) 튜플을 반환하는가
      ③ `python3 -m py_compile proxy_server.py img_pipeline.py nas_lib.py`
  · 이 3개는 아직 운영 서버에서 수행하지 않았습니다.

[미검증]
  · Python 3.11 / 3.12 / 3.13 에서 **전체 앱**이 기동·동작하는지 —
    미검증입니다. 이 샌드박스는 Python 3.13.14 이고, 여기서
    proxy_server.py 는 정상 기동합니다. 그러나 이는 검증 환경이
    샌드박스라는 조건이며, 운영 VPS 재현은 아닙니다.
  · requirements.txt 는 현재 "필수 의존성 없음" 이라는 **거짓 주석**만 있고
    실제 패키지가 없습니다. 이는 수정 대상입니다.


════════════════════════════════════════════════════════════════════
 항목 3 — 파생본 1.84GB 와 로컬 캐시 2.9GB 의 관계
════════════════════════════════════════════════════════════════════

■ 먼저 — 두 수치는 같은 것을 세지 않습니다

[확인 사실 — 실측]
  · 1.84GB = **NAS→가비아로 옮길 사진 파생본의 추정량**
      측정 근거: 무작위 JPEG 24장(150KB 초과, seed=7)을 실제로 변환
        원본 평균            1.70 MB
        thumb(480px, WebP78) 22.1 KB   (77.2배 축소)
        mid(1280px, WebP82)  122.7 KB  (13.9배 축소)
      12,725장으로 외삽:
        원본만            약 20.7 GB
        thumb 만          약  275 MB
        thumb + mid       약 1.80 GB
      → 1.84GB 는 "thumb + mid" 이고, **원본 20.7GB 는 포함하지 않습니다.**

  · 2.9GB = **이 샌드박스의 로컬 캐시 총량** (이전 보고 수치)
      이번에 디렉터리별로 다시 쟀습니다.

[확인 사실 — 로컬 캐시 실측 (du)]
    .static_compress_cache   1.10 GB   2,683 개   → 재생성 가능
    .safe_snapshots          334  MB     687 개   → 재생성 불가(이력)
    .thumb_cache             127  MB   4,158 개   → 재생성 가능
    .media_cache             110  MB       3 개   → 재생성 가능
    .json_mirror             8.3  MB      34 개   → 재생성 가능(단, 장애폴백용)
    .ev_meta_cache           2.9  MB     403 개   → 재생성 가능
    gdrive_store             3.00 GB   1,501 개   → **원본 보관소 (영구)**
    merch_img_upload         80   MB      64 개   → 영구(업로드 원본)
    merch_img                3.4  MB      22 개   → 재생성 가능
    ─────────────────────────────────────────────
    합계                     5.0  GB

  ⚠️ 중요: 2.9GB 라는 이전 수치는 **gdrive_store 를 포함하지 않은 값**으로
     보입니다. 실제 총량은 5.0GB 이고, 이 중 3.0GB 가 gdrive_store 입니다.
     즉 "로컬 캐시 2.9GB" 라는 표현 자체가 부정확했습니다.

■ 포함 관계 — 결론

[확인 사실]
  1.84GB(가비아 파생본) 와 5.0GB(로컬 전체) 는 **겹치는 항목이 없습니다.**
    · 1.84GB 는 NAS 사진 12,725장에서 새로 만들어 가비아에 둘 것
    · 로컬 thumb_cache 127MB 는 **행사 썸네일의 별도 캐시**로,
      NAS `.thumbnails` 에서 받아 온 사본입니다. 다른 대상입니다.
    · 로컬 static_compress_cache 1.1GB 는 **Flutter 정적 자산의 gzip 사본**으로
      사진과 무관합니다. (정적 자산 원본 41MB → 압축 캐시가 1.1GB 인 것은
      과다. 항목 10 의 정리 대상)

  즉 "1.84GB + 2.9GB = 4.74GB 가 필요하다" 는 식의 합산은 **틀렸습니다.**

[수정 제안 — 전체 파생본 합계를 이렇게 표기]
  사진 파생본은 현재 **NAS 와 로컬 양쪽에 중복 생성**됩니다.
    NAS  : 행사관리/.thumbnails  , 행사관리/.views  , 각 항목 _optimized/
    로컬 : .thumb_cache (127MB)  , 일부 .media_cache
  실측한 NAS `.thumbnails` / `.views` 는 **하위 폴더만 있고 파일 크기 합계가
  0 으로 조회**되었습니다. FileStation list 가 하위 폴더를 재귀 합산하지
  않기 때문이며, **실제 파생본 총량은 아직 재지 못했습니다.**

  따라서 v3 에서는 아래처럼 씁니다.
    · 가비아에 둘 사진 파생본      : 약 1.8 GB  (추정, 실측 외삽)
    · NAS 에 이미 있는 파생본      : 미측정
    · 이 샌드박스 로컬 캐시 전체    : 5.0 GB (실측, gdrive_store 3.0GB 포함)
    · 서버에 필요한 총 용량         : **산정하지 않음** (항목 10 의 정책 확정 후)

  이 수치를 "서버 필요 용량" 으로 제시하지 않습니다. 지적대로 파생본은
  정책(무엇을 어디에 둘지)이 정해져야 총량이 정해집니다.

[미검증]
  · NAS 쪽 파생본(.thumbnails/.views/_optimized) 실제 총 바이트 — 미측정.
  · 12,725장 전량 변환 시 실제 총량 — 외삽이며 실측 아님.
  · 영상 썸네일·포스터 프레임 파생본 규모 — 미측정.

 항목 4 — 영상이 정말 NAS→브라우저 직접인가 (정정)
════════════════════════════════════════════════════════════════════

■ 정정: 영상은 NAS 에서 브라우저로 직접 가지 않습니다

제 v2 의 "영상은 가비아 트래픽을 쓰지 않는다" 는 **틀렸습니다.**
지적하신 대로 Range 206 지원만 보고 결론낸 것이 오류였습니다.
아래는 실제 요청·코드·송신량 3가지로 확인한 결과입니다.

[확인 사실 ① — 최종 요청 URL 과 응답]
  실제 영상 파일: 2026 / "20260614_풍무성당 2190 표지우 범진급식" / IMG_4140.MOV
  선언 크기: 93,780,686 바이트

  요청: GET /api/event/f2?year=2026&title=...&key=media&name=IMG_4140.MOV
        Range: bytes=0-1023
  응답: HTTP 206
        Content-Range: bytes 0-1023/93780686
        Content-Length: 1024
        Accept-Ranges: bytes
        Location: (없음)
        Cache-Control: no-store
        실제 수신 바이트: 1,024

  요청: 같은 URL, Range: bytes=50000000-50000999  (중간 seek)
  응답: HTTP 206
        Content-Range: bytes 50000000-50000999/93780686
        실제 수신 바이트: 1,000

  요청: 같은 URL, Range 없음 (전체)
  응답: HTTP 200
        실제 수신 바이트: 93,780,686  ← 선언 크기와 정확히 일치
        소요: 11.76초

  ⭐ 핵심: **Location 헤더가 없습니다.** NAS 로 리다이렉트하지 않습니다.
     즉 93MB 전량이 이 Python 프로세스를 통과해 클라이언트로 나갑니다.

[확인 사실 ② — Python 응답 처리 코드]
  `_serve_nas_file()` (proxy_server.py:18348)
    · 파일 전체 크기를 `NAS.get_info()` 로 메타데이터만 얻고
    · Range 구간이 작으면 `NAS.read_range()` 로 그 구간만 읽어
    · `self.wfile.write(...)` 로 **클라이언트에 직접 씁니다.**

  코드 내 송신 지점 (`_pump_bytes` 안, proxy_server.py:18530~18566):
    :18530  `self.wfile.write(view[i:i + CHUNK])`
    :18536  `self.wfile.write(reader(path, start, length))`
    :18543  `self.wfile.write(b)`
    :18559  `self.wfile.write(b)`
    :18566  `self.wfile.write(memoryview(data)[start:start + length])`
  로컬 캐시 경로(`_serve_local_range`, :18455)의 송신 지점:
    :18507  `self.wfile.write(b)`

  · NAS 로의 3xx 리다이렉트 코드 존재 여부를 검색:
    `Location` + `5001` / `redirect` + `nas` 조합 → **검색 결과 없음**
    (참고: `39.123.241.4` 는 proxy_server.py 안에 **0회** 등장합니다.

[확인 사실 ③ — 송신량]

 항목 7 — /readyz 설계 ( _load_json 동작 확인 후 )
════════════════════════════════════════════════════════════════════

■ 먼저 _load_json 을 읽었습니다 (proxy_server.py:4727)

[확인 사실 — 동작 순서]
  1. `_JSON_CACHE` 에 있고 신선하면 → 즉시 반환
  2. 신선하지 않지만 `age < ttl + 여유` 이면 → **묵은 값을 먼저 반환**하고
     `_json_refresh_bg` 로 백그라운드 갱신
  3. 그 외 → `_mirror_read()` 를 **먼저** 시도 (로컬 미러)
  4. 미러도 없으면 `NAS.exists()` → `NAS.read()`
  5. 성공하면 `_accept()` 가 캐시 + 미러에 기록
  6. **예외가 나면 절대 raise 하지 않습니다.**
     캐시본이 있으면 그걸, 없으면 `default` 를 반환합니다.
  7. `_is_empty_list` 가드: 비어 있지 않은 기존 값을 빈 리스트로
     덮어쓰지 못하게 막습니다.

[확인 사실 — 이것이 /readyz 설계에 주는 제약]
  · `_load_json` 은 **실패해도 성공처럼 보입니다.**
    NAS 가 죽어도 `default` 를 돌려주므로 호출부는 알 수 없습니다.
  · 따라서 "데이터를 읽었다" 를 readiness 신호로 쓸 수 없습니다.
  · 미러가 살아 있으면 NAS 가 죽어도 정상 응답합니다(설계 의도).

■ /readyz 설계 (수정 제안)

[수정 제안 — 3단계 분리]
  `GET /readyz` 는 아래를 **각각 따로** 보고합니다.
  전체를 한 값으로 뭉치지 않는 것이 핵심입니다.

    {
      "ok": true,                       // 프로세스가 요청을 받는가
      "process": { "up": true, "pid": ..., "uptimeSec": ... },

      "static": {
        "dir": "<TSAK_STATIC_DIR 실제값>",
        "exists": true,                 // 디렉터리 존재
        "readable": true,               // R|X 권한
        "indexHtml": true,              // index.html 존재
        "ready": true                   // 위 3개 AND
      },

      "nas": {
        "reachable": true,              // get_info() 성공 여부 (짧은 타임아웃)
        "latencyMs": 41,
        "lastOkAt": "2026-11-20T06:18:34"
      },

      "cache": {
        "mode": "mirror-healthy",       // nas-healthy | mirror-healthy | both-down
        "mirrorFiles": 34,
        "mirrorWritable": true,
        "staleEntries": 2
      },

      "writable": {
        "mirror": true,                 // 미러 디렉터리에 쓸 수 있는가
        "snapshotDir": true,
        "nasWriteProbe": false          // 실제 쓰기는 하지 않고 권한만 확인
      }
    }

[수정 제안 — 상태 코드 규칙]
  · `200` : 프로세스 살아 있음 + static.ready + (nas.reachable 또는 cache.mode != "both-down")
  · `503` : static.ready == false  또는  cache.mode == "both-down"
            또는  mirrorWritable == false
  · 즉 **NAS 장애만으로는 503 을 내지 않습니다.**
    미러가 정상이면 서비스는 실제로 동작하기 때문입니다.
    다만 `nas.reachable: false` 로 **명시**해 모니터가 구분할 수 있게 합니다.

[수정 제안 — 부분 장애 시 동작 명시]
  · NAS 죽음 + 미러 정상  → 200, mode="mirror-healthy", 경고 로그
    (읽기는 되고 쓰기는 실패. 쓰기 실패는 기존 `_on_save_blocked` 카운터로 관측)
  · NAS 죽음 + 미러 없음   → 503, mode="both-down"
  · 디스크 가득            → 503 (mirrorWritable=false)
  · static 경로 오류       → 503 (항목 8 의 실제 테스트에서 확인된 침묵 실패)

[확인 사실 — 현행 /api/health 의 문제]
  `/api/health` (:18581) 는 인증 없이 `ok / paused / ts / saveGuard` 만 냅니다.
  위 3가지(NAS/미러/static)를 구분하지 못합니다.
  실측: STATIC_DIR 이 잘못돼 정적 파일이 전혀 안 나오는 상태에서도
        `/api/health` 는 **HTTP 200** 을 반환했습니다 (항목 8 참조).
  → `/readyz` 를 health 와 **별도로** 두는 것이 맞습니다.
     (health = 프로세스 생존, readyz = 서비스 가능)

[미검증]
  · Nginx / 로드밸런서가 이 /readyz 를 실제로 어떻게 쓸지 — 미정.
  · `_load_json` 의 TTL 실제 값과 `_JSON_STALE_EXTRA` 값 — 코드 확인 필요.

■ 정정: 비공개 사진에 public·immutable 을 붙이고 있었습니다

    · `immutable` 은 최대 30일 동안 재검증 없이 그 사본을 쓴다는 뜻입니다.
      사진을 삭제·교체해도 최대 30일간 옛 사본이 보일 수 있습니다.
    · `no-store` 를 붙이던 `_cors()` 의 보안 의도(F02, 개인정보 캐시 금지)를

■ 정정: "재방문 트래픽 0" 은 성립하지 않습니다

[확인 사실]

    서버가 트래픽을 보장하는 것이 아닙니다.
  · 사용자가 캐시를 지우면, 다른 브라우저·기기면, 시크릿 모드면
    **다시 받습니다.**
  · `Vary: Origin` 이 붙어 있어 출처가 다르면 캐시가 분리됩니다.
  · 따라서 정확한 표현은 "**재방문 시 브라우저 캐시를 쓸 가능성이 높다**"

[수정 제안 — 정책표]

■ 지적 수용: data 폴더 생성 ≠ 이중 저장

[확인 사실]
  디렉터리가 있다는 사실만으로 용량이 두 배가 되지 않습니다.
  실제로 두 배가 되는 것은 **같은 내용이 양쪽에 실제로 쓰였을 때**입니다.

    · .static_compress_cache 1.1GB — Flutter 정적 자산(41MB)의 gzip 사본.

    · .safe_snapshots 334MB — 저장 직전 JSON 회전 백업. **유일본에 가까움**.

 항목 11 — NAS 5001 인터넷 공개를 전제하지 않기
════════════════════════════════════════════════════════════════════

■ 지적 수용

[확인 사실]
  현 구성은 `nas.base = https://39.123.241.4:5001` 입니다.
  프록시 서버가 이 주소로 **직접** 접속합니다.
  여기서 파생되는 사실:
    · 이 프록시가 도는 곳에서 5001 이 도달 가능해야 NAS 가 동작합니다.
    · 샌드박스(외부 클라우드)에서 도달한다는 것은 **5001 이 인터넷에
      열려 있다**는 뜻입니다. (실측: NAS 읽기·쓰기 모두 성공)
    · 즉 현재 구조는 **NAS 5001 공개를 사실상 전제**하고 있습니다.
  이는 보안상 바람직하지 않으며, 운영 서버가 가비아로 가면
  "가비아 서버 IP 만 5001 허용" 으로 좁힐 수는 있습니다.
  다만 그것도 5001 을 여전히 인터넷에 노출하는 구성입니다.

■ 이 구조에서 지켜지는 것 (확인 사실)

  · NAS 관리자 계정·세션은 **브라우저에 노출되지 않습니다.**
    브라우저는 프록시의 API 만 호출하고, 프록시가 서버 측에서
    NAS 에 로그인합니다. 쿠키는 프록시 프로세스 메모리에만 있습니다.
    이 부분은 지적하신 우려와 달리 **현재도 지켜지고 있습니다.**
  · 브라우저로 나가는 쿠키는 `tsak_sid` (HttpOnly, SameSite=Strict) 뿐입니다.

  ⚠️ 단, 항목 5 의 문제(앱 비밀번호 = NAS 비밀번호, 그리고 그것이
     JS 번들에 평문)가 있으므로, **비밀번호가 같다는 점이 실질적 위험**입니다.
     "세션은 노출되지 않는다" 와 "비밀번호가 노출되었다" 는 별개 문제이며
     후자가 더 급합니다. (항목 5 의 2단계)

■ 대안 (수정 제안)

[수정 제안 — 3가지, 선호 순서대로]

  대안 A : NAS → 가비아 서버로 **역방향 터널** (권장)
    · 가비아 서버에서 `ssh -R` 로 NAS 측 포트를 가비아 서버 localhost 에 연결
    · `nas.base` 를 `https://127.0.0.1:5001` 로 변경
    · NAS 방화벽에서 5001 **완전 차단** (인터넷 노출 0)
    · 장점: 노출 제거 + 코드 변경 최소(config 한 줄)
    · 단점: 터널 상시 유지 필요(systemd + 자동 재연결), 터널 죽으면 NAS 접근 불가
              → 미러 폴백이 있으므로 읽기는 버팀(항목 7)

  대안 B : **제한된 HTTPS 다운로드 서비스** (지시서 표현)
    · NAS 에서 공개하는 API 를 FileStation 전체가 아니라
      **읽기 전용·특정 폴더 한정·토큰 인증**의 좁은 서비스로 대체
    · 예: NAS 의 Web Station 에 작은 리버스 프록시를 두고
          경로 화이트리스트(`/92_Tiger_app_data/TSAK_인가자관리` 하위만) +
          공유 토큰 헤더 검사
    · 장점: 5001 관리자 인터페이스를 인터넷에서 제거
    · 단점: NAS 에 별도 서비스 설치 필요. FileStation Upload API 를
            쓰는 쓰기 경로(`nas_lib.write`)를 어떻게 처리할지 설계 필요

  대안 C : **가비아 서버를 NAS 의 VPN 클라이언트로**
    · WireGuard 등으로 가비아 서버만 NAS 사설망에 참여
    · `nas.base` → NAS 사설 IP
    · 장점: 노출 0, 성능 좋음
    · 단점: NAS 에 VPN 서버 패키지 설치·설정 필요, 관리 부담

[수정 제안 — 어느 대안이든 지켜야 할 원칙]
  · 브라우저는 NAS 를 **절대 직접 호출하지 않습니다.** (현재 지켜짐, 유지)
  · NAS 자격증명은 프록시 프로세스만 보유합니다. (현재 지켜짐, 유지)
  · `nas.base` 를 코드에 하드코딩하지 않고 설정으로 유지합니다. (현재 지켜짐)
  · 대안 A/B/C 어느 것도 **이번 승인 범위에 넣지 않습니다.**
    NAS 설정 변경이 필요하므로 별도 승인 사항입니다.

[미검증]
  · NAS 가 SSH 역방향 터널을 허용하는 설정인지 — 미확인.
  · NAS 방화벽에서 5001 을 닫았을 때 다른 앱(모바일 앱 등)이 쓰는지 — 미확인.

════════════════════════════════════════════════════════════════════
 항목 12 — JSON 저장소 원자성·동시성·백업
════════════════════════════════════════════════════════════════════

■ 확인 사실 ① — _save_json 은 원자적이지 않습니다

  proxy_server.py `_save_json(path, obj, force=False)` 동작 순서:
    1. `_json_gen_bump(path)` — 세대 증가 (경쟁 창 닫기 목적)
    2. `_guard_destructive_save()` — 파괴적 저장이면 **False 반환하고 중단**
    3. `_safe_snapshot(path)` — 회전 백업 (실패해도 계속)
    4. `NAS.write(path, json.dumps(...))` — **NAS 에 통째로 덮어쓰기**
    5. `_JSON_CACHE[path] = (obj, time.time())` — 캐시 갱신
    6. `_lpi_invalidate`, `_mirror_write()`

  원자성이 없는 지점:
    · 4번이 `NAS.write()` → `nas_lib.write()` 입니다.
      이 함수는 `SYNO.FileStation.Upload` 에 `overwrite: true` 로
      **파일을 직접 덮어씁니다.**
      임시 파일에 쓰고 rename 하는 절차가 **없습니다.**
    · 즉 쓰기 도중 실패하면 **파일이 반쯤 쓰인 상태**로 남을 수 있습니다.
    · 로컬 미러(`_mirror_write`)도 같은 방식입니다.

■ 확인 사실 ② — 실패 반환이 무시됩니다

  코드 주석에 명시되어 있습니다(:`_save_json` 내부):
    "⚠️ 차단되면 False 를 돌려준다. 호출부 103곳이 반환값을 무시하므로,
       차단 사실이 조용히 묻히지 않도록 아래에서 전역 카운터에 남긴다."

  → `_guard_destructive_save` 가 저장을 막아도 **호출부는 성공으로 믿습니다.**
    관측 수단은 `/api/health` 의 `saveGuard.blockedCount` 뿐입니다.
    실측: 현재 blockedCount = 0.

■ 확인 사실 ③ — 전역 쓰기 락이 없습니다

  `grep` 결과 존재하는 락:
    LOCK, _SESS_LOCK, _ACCESS_LOG_LOCK, _BOARD_WRITE_LOCK,
    _REVIEW_WRITE_LOCK, _IPWATCH_LOCK, _MEMBER_WRITE_LOCK, _HISTORY_LOCK
  → `_save_json` 전체를 감싸는 락은 **없습니다.**
    게시판·후기·회원은 개별 락이 있으나, 그 외 JSON 은 무방비입니다.

■ 실측 ① — 교차 프로세스 동시 쓰기 (원자성 결함 재현)

  같은 파일을 3개 프로세스가 각 60회 읽기-수정-쓰기 했습니다.
  (매 회 디스크에서 읽고, 통째로 덮어쓰기 — `_save_json` 과 동일 의미론)

    기대: 180건
    실제:  62건
    손실: 118건 (65.6%)
    추가: 2개 프로세스가 json.decoder.JSONDecodeError 발생
          ("Extra data", "Expecting value") ← **반쯤 쓰인 파일을 읽음**

  이는 "동시에 저장하면 데이터가 사라지고 파싱 오류까지 난다" 는
  직접 증거입니다.

■ 실측 ② — 단일 프로세스 다중 스레드 (조건부로 안전)

  동일 조건을 8개 스레드로 시험했을 때는 손실 0 이었습니다.
  이유: `_JSON_CACHE` 가 **같은 객체를 돌려주므로** 스레드들이
  사실상 같은 리스트를 제자리 수정하고, 마지막에 한 번 덮어써도
  내용이 합쳐져 있었습니다.

  ⚠️ 그러나 이 "안전"은 **우연에 가깝습니다.**
    · 캐시가 만료되어 각자 디스크에서 읽으면 즉시 실측 ①의 상태가 됩니다.
    · `_json_refresh_bg` 백그라운드 갱신과 사용자 저장이 겹치면
      같은 문제가 납니다. (`_json_gen_bump` 는 이 창을 **줄일 뿐** 닫지 않음)

■ 수정 제안

[수정 제안 — 3단계]

  1단계 (즉시, 위험 낮음): 저장 직렬화
     `_SAVE_LOCK = threading.Lock()` 을 추가하고
     `_save_json` 의 3~6번 구간을 `with _SAVE_LOCK:` 으로 감쌉니다.
     → 단일 프로세스 내 경쟁은 완전히 제거됩니다.

  2단계 (중기): 원자적 쓰기
     · 로컬: `path.tmp` 에 쓰고 `os.replace()` (같은 파일시스템이면 원자적)
     · NAS: `FileStation.Upload` 를 임시 이름으로 올린 뒤
            `FileStation.Rename` 으로 교체.
            (NAS 업로드가 원자적 rename 을 지원하는지 **미검증**)
     · 최소한 "쓰기 실패 시 이전 파일이 남는" 성질을 확보해야 합니다.

  3단계 (구조): 실패 반환을 무시하지 않기
     · `_save_json` 이 False 를 돌려주면 호출부가 사용자에게 알리도록
       최소한 **API 응답에 `saved: false` 를 포함**시킵니다.
     · 103곳 일괄 수정은 위험하므로, 재무·회원·참가자 등
       **중요 저장 경로부터** 순차 적용합니다.

■ 확인 사실 ④ — NAS 원본은 독립 백업이 아닙니다

  · NAS 는 **하나의 물리 장치**입니다. RAID 가 있어도 그것은
    디스크 고장 대응이지, 랜섬웨어·실수 삭제·화재 대응이 아닙니다.
  · 이 샌드박스에 `backups_pruned_20261014_210713.tar.gz` (342MB) 가
    있는데, 이는 **같은 서버 안의 백업**입니다. 서버가 사라지면 함께 사라집니다.
  · 즉 현재 **오프사이트 독립 백업이 확인되지 않았습니다.**

■ 백업 주기·손실 허용 범위 — 소유자 확인 요청

  [소유자 확인 필요] 아래 4개는 제가 정할 수 없습니다.

    ① 하루에 몇 번 저장이 일어납니까?
       (현재 JSON 저장 빈도를 계측하지 않았습니다)
    ② 서버가 죽었을 때 **몇 시간 전 데이터까지** 돌아가면 받아들이실 수 있습니까?
       (RPO — 허용 데이터 손실 기간)
    ③ 복구에 **얼마나 걸려도** 괜찮습니까? (RTO)
    ④ 오프사이트 백업 수단이 있습니까?
       (외장하드 정기 복사 / 클라우드 / 다른 NAS)
       현재 확인된 것은 없습니다.

  [수정 제안 — 위 답을 받은 뒤 정할 것]
    · `.safe_snapshots` 회전 백업을 NAS 외부로 주기 복사
    · 주 1회 전체, 매일 증분 (빈도는 ①의 답에 따름)
    · 복구 리허설을 최소 1회 실제로 수행 (지금은 복구 절차가
      `restore_snapshot.py` 로 존재하나 **실행해 본 적 없음**)

[미검증]
  · FileStation Rename 이 원자적 교체를 보장하는지 — 미검증.
  · `_json_refresh_bg` 와 사용자 저장이 실제로 충돌한 사례 — 미확인.
  · JSON 저장 빈도 — 계측하지 않음.
  · `restore_snapshot.py` 복구 리허설 — 미실시.
