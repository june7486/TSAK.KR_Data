1. A안 폐기 · B안 구체화 · NAS 자격증명 별도 긴급 대응

1-1. A안을 채택하지 않는 이유 [확인 + 동의]

귀 지적: "공용 비밀번호를 서버에서 브라우저 메모리로 내려주는 A안은

보안 해결책으로 채택하지 않는 방향을 권고합니다."

동의합니다. A안은 비밀번호를 "파일에 두지 않는다"는 문제만 옮깁니다.

실제 위협 모델에서 A안이 막지 못하는 것:

· 브라우저 메모리에 있는 문자열은 개발자도구·메모리 덤프·악성 확장으로

읽힙니다. 파일보다 안전하지 않고, 오히려 수명이 길어집니다

(탭이 살아있는 동안 계속 존재).

· 프록시가 죽으면 앱 전체가 죽습니다. A안은 가용성을 프록시에

완전히 종속시키는데, 이 프록시는 단일 프로세스입니다.

· 무엇보다 A안은 "누가 무엇을 볼 수 있는가"를 전혀 다루지 않습니다.

비밀번호를 아는 사람은 전부 같은 권한입니다. 이건 권한 설계가 아니라

비밀 공유입니다.

[확인] 참고로 현재 빌드 산출물에 비밀번호 문자열이 남아 있는 것을

v3 에서 확인했습니다(build/web/main.dart.js). A안으로 가면 이 문자열이

"서버가 내려주는 값"으로 바뀔 뿐, 여전히 브라우저에 존재합니다.

1-2. B안 구체화 [제안]

원칙: 브라우저는 자기 세션 토큰만 갖는다. NAS 자격증명은

프로세스 메모리에만 있고, 어떤 응답에도 실리지 않는다.

(a) 인증

· 로그인은 아이디/비밀번호 → 서버가 세션 발급.

· 세션 쿠키는 이미 SameSite=Strict / HttpOnly 입니다.

[확인] proxy_server.py 의 세션 쿠키 발급부에서 확인.

Secure 는 _is_https_req() 일 때만 붙습니다 → HTTPS 종단이

프록시 앞에 있어야 이게 실제로 동작합니다. [가정] 현재 가비아

구성에서 TLS 종단 위치를 확인하지 못했습니다.

(b) 권한 검사는 매 요청 서버에서

· 세션에 tier 를 저장하고, 요청마다 _auth_ok(need) 로 판정합니다.

[확인] 이미 이 구조입니다. 다만 아래 (c) 의 구멍이 있습니다.

· need=None(로그인만 하면 통과) 인 경로가 다수입니다.

이걸 "공개 자료"와 "회원 자료"로 다시 나눠야 합니다.

(c) 현재 권한 모델의 구멍 (제 코드 결함)

[확인] _auth_ok("admin") 은 tier in ('app','master') 또는

s.get("grantedAdmin") 입니다. 즉 세션 객체에 grantedAdmin 키가

참이면 관리자입니다. 이 키를 세션에 넣는 경로가 하나라도

사용자 입력에서 오면 권한 상승입니다.

→ 확인 필요. 제가 아직 이 주입 경로를 전수 추적하지 못했습니다.

[미검증] 로 표시합니다. B안 확정 전에 반드시 추적해야 합니다.

(d) NAS 자격증명 격리

· config.json 은 chmod 600, 소유자는 프록시 실행 계정. [확인]

· 문제: nas.pw == auth.app (동일 문자열). [확인] v3 에서 확인.

즉 앱 로그인 비밀번호를 아는 사람이 NAS 계정 비밀번호도 압니다.

이건 B안을 만들어도 그대로 남는 구멍입니다.

· 제안: NAS 전용 계정을 따로 만들고, 그 계정은

BASE 디렉터리 하위만 접근하도록 Synology 공유폴더 권한을

제한합니다. 프록시는 그 계정만 씁니다.

1-3. NAS 자격증명 분리·폐기는 별도 긴급 대응으로 [제안]

귀 지적대로 이 문서에 섞지 않습니다. 별도 문서로 분리하고,

여기에는 목차와 담당만 적습니다.

[별도 문서 A] NAS 자격증명 분리·폐기 긴급 대응

A-1. 유출 가능성이 있는 자격증명 목록화 (범위·보관 위치·사용처)

A-2. 신규 NAS 전용 계정 생성 + 최소 권한 부여

A-3. 프록시 재기동으로 신규 자격증명 반영 (구 자격증명 무효화)

A-4. 무효화 후 정상 동작 확인 (읽기/쓰기/이미지 파생/백업)

A-5. 되돌리기 절차 (구 자격증명 복원이 필요한 경우의 조건)

A-6. 재발 방지: 설정 파일에 앱 비밀번호와 NAS 비밀번호를

같은 값으로 두지 않는다는 규칙을 코드로 강제(시작 시 검사)

[제안] A-6 은 지금 바로 넣을 수 있습니다. 시작 시

config.json 의 nas.pw 와 auth.app 이 같으면 경고가 아니라

기동 거부로 처리할지 결정이 필요합니다. 이건 운영자 판단이라

제가 임의로 정하지 않았습니다.

2. 허브 하위 경로 통합 철회 — 독립 도메인 루트 유지

2-1. 철회 [철회]

v3 §6 에서 제가 /tsak, /scout, /scheduler 를 한 허브 아래 하위 경로로

묶는 그림을 제시했습니다. 철회합니다.

귀 지적: "각 독립 도메인의 루트에서 서비스하는 기존 계약을 유지하세요.

Nginx 는 도메인별 분기, 각 앱은 독립 프로세스로 구성합니다."

이게 맞습니다. 제 그림의 문제를 제가 정확히 적습니다:

· Flutter Web 앱은 기본 경로(base href)를 전제로 빌드됩니다.

루트가 아닌 하위 경로로 옮기면 base href, 라우팅, 서비스워커,

정적 자산 경로가 전부 영향을 받습니다. 이건 설정 한 줄이 아닙니다.

[확인] 이 앱은 실제로 리다이렉트 없이 프록시가 직접 정적 파일을

서빙하는 구조이고, STATIC_DIR 하나로 루트를 잡습니다.

즉 지금 "루트 계약"에 이미 맞춰져 있습니다.

· 한 프로세스가 여러 앱을 서빙하면 장애 격리가 사라집니다.

지금 프록시는 단일 프로세스입니다. 여기에 scout 까지 얹으면

scout 장애가 tsak 장애가 됩니다. 하위 경로 통합은 이 결합을

구조적으로 고정시킵니다.

· 도메인별 분기는 DNS·인증서·쿠키 스코프를 도메인 단위로

다룰 수 있게 합니다. 하위 경로는 쿠키 Path 로 흉내내야 하고,

이건 도메인 격리보다 약합니다.

2-2. 수정 설계 [제안]

  · tsak.kr       → 루트("/")에서 TSAK 앱. 독립 프로세스.

· scout 도메인 → 루트("/")에서 scout 앱. 별도 프로세스.

  · scheduler     → 루트("/")에서. 별도 프로세스.

· Nginx 는 server_name 기준으로 upstream 만 다르게 잡습니다.

경로 재작성(rewrite /tsak/ → /)을 하지 않습니다.

경로 재작성이 들어가면 정적 자산과 API 가 같이 깨집니다.

· 각 프로세스는 자기 STATIC_DIR 과 자기 포트를 갖습니다.

[확인] TSAK_STATIC_DIR 환경변수로 주입 가능하게 이미 되어 있습니다

(proxy_server.py 의 STATIC_DIR 정의부).

2-3. 다만 이 설계에는 제가 v3 에서 지적하지 않은 위험이 있습니다 [가정]

프로세스가 늘어나면 §9 의 gdrive_store 문제가 배로 커집니다.

gdrive_store 를 동시에 만지게 됩니다. 이건 항목 4 의 다중 프로세스

문제와 정확히 같은 뿌리입니다.

[확인] 실제로 제가 이번 조사 중에 테스트용 프록시 3개를 같은 cwd 로

띄워둔 것을 발견하고 종료했습니다 (포트 5091/5092/5093/5099).

즉 이 위험은 가상이 아니라 제가 이미 한 번 저지른 일입니다.

[제안] 앱별 프로세스 분리와 함께 상태 디렉터리도 앱별로 분리해야

합니다. .json_mirror / gdrive_store / .media_cache / .safe_snapshots 를

cwd 기준 상대경로로 두면 안 됩니다. 환경변수로 절대경로를 주입하고,

시작 시 서로 다른 프로세스가 같은 경로를 쓰면 기동을 거부하는 검사가

필요합니다. 이 검사는 아직 없습니다. [확인: 없음]

3-1. 두 가지를 구분합니다 [확인 + 동의]

귀 지적: "NAS 관리 자격증명의 브라우저 노출 금지와 NAS 측 제한된

맞습니다. v3 에서 제가 이 둘을 뭉쳐서 "NAS 직접 접근은 위험"으로

처리한 것이 부정확했습니다. 구분합니다.

구분 A — 브라우저에 NAS 관리 자격증명을 주는 것

· 절대 금지. 대상 아님. 이건 관리자 권한 전체를 브라우저에 두는 것.

· 협상의 여지가 없는 항목입니다.

발급한 접근 경로. 관리 자격증명이 아닙니다.

· 조건: 그 제한 계정이 BASE 하위 특정 폴더만 읽을 수 있어야 하고,

쓰기·삭제·목록 전체 조회 권한이 없어야 합니다.

3-2. 왜 이게 비용 문제인가 [확인]

· Range 요청 2건 → 206 / 1,024 B, 206 / 1,000 B (정상)

· Range 없는 요청 1건 → 200 / 93,780,686 B / 11.76초

· Location 헤더: 없음

즉 전체 재생 시 영상 바이트가 파이썬 프로세스를 그대로 통과합니다.

프록시가 파일을 대신 전달하므로, 그 바이트는 가비아 회선을 나갑니다.

이 구조에서 구분 B 를 쓰면 영상 바이트가 가비아를 통과하지 않게

할 수 있습니다. 이게 소유자의 비용 절감 목표와 직접 연결됩니다.

3-3. VPN·SSH 터널에 대한 제 철회 [철회]

v3 §11 d안에서 제가 "터널을 쓰면 송신량 문제가 해결된다"는 함의를

남겼습니다. 철회합니다.

귀 지적이 정확합니다: "VPN·SSH 터널만으로 가비아 송신량이 사라지지는

않습니다."

· 터널은 경로를 암호화합니다. 데이터가 가비아 회선을 지나지 않게

만드는 것은 목적지·경로의 문제이지 암호화의 문제가 아닙니다.

· 브라우저 → 가비아 → 터널 → NAS 로 흐르면 가비아를 여전히 지납니다.

· 가비아를 안 지나려면 브라우저가 가비아를 거치지 않고 NAS 에

도달해야 합니다. 그게 구분 B 이고, 그건 터널이 아니라

접근 경로 설계입니다.

· 반대로 브라우저 → NAS 직접이 안 되는 이유(자체서명 인증서, CORS,

포트 개방)는 v3 에서 정리한 그대로입니다. 구분 B 는 그 제약을

우회하는 게 아니라, 제한된 서비스로 감싸서 해결하는 것입니다.

3-4. 이 항목의 상태

구분 A 금지 [확인] / 구분 B 검토 대상 인정 [확인]

/ 터널이 송신량을 없앤다는 함의 철회 [철회]

/ 구분 B 의 실제 구성(공유 링크 vs 제한 계정 vs 별도 서비스) [미검증]

→ NAS 측 설정이 필요해서 제가 실측하지 못했습니다.

4. _save_json 저장 구간 잠금으로 경쟁이 해결된다고 말하지 않겠습니다

4-1. 먼저 제가 실측한 것 — 단일 프로세스에서는 저장 구간 잠금이 효과가 있습니다

[확인]

귀 지적: "_save_json 저장 구간만 잠그는 것으로 읽기–수정–쓰기 경쟁이

완전히 해결된다고 표현하지 마세요."

"완전히 해결된다"고 표현하지 않겠습니다. 다만 **어디까지 효과가 있고

어디부터 없는지**를 실측으로 나눠서 제출합니다. 이 구분이 없으면

설계 방향을 잘못 잡습니다.

실험: 단일 프로세스, 8 스레드 × 40회, 매 반복마다 캐시를 강제로

우회하여 파일에서 읽고(read) → append → write.

(캐시가 살아 있으면 경쟁이 가려지므로 강제 미스)

결과

    · 락 없음        : 기대 320 / 실제 41  / 손실 279 (87.2%)
    · 쓰기만 락      : 기대 320 / 실제 320 / 손실 0   (0.0%)

해석 (정직하게)

· 단일 프로세스 + 캐시 미스 상황에서는 저장 구간만 잠가도 손실이

사라집니다. 왜냐하면 이 실험에서 읽기와 쓰기가 같은 임계구역

안에 들어왔기 때문입니다(하네스에서 락이 load+save 를 함께 감쌌음).

· 즉 "저장만 잠그면 된다"가 아니라 **"읽기부터 쓰기까지 한 임계구역

으로 묶으면 단일 프로세스에서는 된다"** 가 실측이 말하는 것입니다.

이 차이가 중요합니다. 저장 구간만 잠그고 읽기를 밖에 두면

읽기-쓰기 사이 창이 남습니다.

· 귀 지적은 이 창을 지적한 것으로 이해합니다. 맞습니다.

4-2. 다중 프로세스에서는 저장 구간 잠금이 무력합니다 [확인]

실험: 3개 프로세스 × 60회 읽기-수정-쓰기 (같은 파일)

결과: 기대 180 / 실제 62 / 손실 118 (65.6%)

+ JSONDecodeError 2건 ("Extra data", "Expecting value")

이유는 명확합니다. threading.Lock 은 프로세스 안에서만 유효합니다.

프로세스가 2개 이상이면 락은 서로를 보지 못합니다.

이게 이론이 아니라는 증거: 제가 이번 조사 중에 테스트용 프록시

3개가 같은 cwd 로 살아 있는 것을 발견했습니다

(포트 5091/5092/5093/5099, PIDs 116268/116562/116650/116806).

제가 만든 것이고, 제가 종료했습니다. 실제로 그 상태에서

.json_mirror 와 gdrive_store 를 공유하고 있었습니다.

4-4. 캐시·백그라운드 갱신은 이미 일부 방어가 있습니다 [확인 — 귀 지적에

대한 반론이 아니라, 기존 방어를 정확히 기록하기 위함]

_json_refresh_bg(path) 에는 세대 카운터 가드가 있습니다.

백그라운드 갱신을 시작할 때 세대를 캡처하고, 끝났을 때 세대가

바뀌었으면 결과를 버립니다. 즉 "낡은 스냅샷으로 덮어쓰기"는

이미 막혀 있습니다.

또 _JSON_REFRESHING 집합으로 같은 경로 중복 갱신도 막습니다.

그래도 남는 것:

· 이 가드는 프로세스 안에서만 동작합니다(세대 카운터가 메모리).

· _save_json 은 _json_gen_bump 를 쓰기 전에 하므로 창을 줄이지만,

NAS 왕복 동안 다른 스레드가 읽은 값으로 저장을 완료하는 경로는

여전히 남습니다.

· 근본 해결은 아니고 완화입니다. 완화로 표기합니다.

4-5. 일관성 설계 [제안]

(1단계) 대상 축소 — 위험을 먼저 줄인다

· 쓰기가 빈번하고 손실이 치명적인 파일을 목록화합니다.

후보: DB_FILE(회원), EUNHA_DB_FILE, FIN_FILE, CFG_FILE, MERCH_FILE,

RES_ORDER_FILE, NOTIFY_FILE.

· 이 목록의 파일은 단일 작성자 원칙을 적용합니다.

즉 쓰기 경로를 하나의 큐로 모으고, 큐 소비자가 유일한 작성자가

됩니다. 읽기는 자유. 이러면 애플리케이션 수준 RMW 가

직렬화됩니다.

(2단계) 프로세스 간 직렬화

· 파일별로 .lock 파일을 두고 fcntl.flock(배타) 으로 감쌉니다.

임계구역 = [읽기 시작, 쓰기 완료].

· 락 획득 실패 시 즉시 실패가 아니라 짧은 백오프 재시도

(예: 20ms 간격, 최대 2초). 이후에도 실패하면 503 + 명시적 오류.

조용히 성공으로 반환하지 않습니다 — 이게 지금의 문제입니다.

· 락 파일은 상태 디렉터리와 함께 앱별로 분리합니다(항목 2-3).

(3단계) 쓰기 실패를 관측 가능하게

· 현재 _save_json 은 실패해도 False 를 돌려주고, 호출부 103곳이

반환값을 무시합니다(코드 주석에 이미 적혀 있음).

· 제안: 반환값 무시를 정적으로 검출하는 테스트를 추가합니다.

(AST 로 _save_json 호출부를 훑어 반환값 사용 여부를 검사)

· 차단·실패 건수는 이미 /api/health 의 saveGuard 로 노출됩니다.

이건 인증 없이 보입니다 → 항목 7 에서 인증 경로로 옮길 것을

제안합니다.

(4단계) 회귀 테스트 [제안 — 아직 작성·실행하지 않았습니다]

· T-A: 단일 프로세스 8스레드 × 100회, 캐시 강제 미스

기대 = 정확히 800, 허용 손실 0

· T-B: 3 프로세스 × 100회, 같은 파일

기대 = 정확히 300, 허용 손실 0

· T-C: 백그라운드 갱신과 저장이 겹칠 때 최종 값이

"마지막 저장값"인지 확인

· T-D: 락 획득 타임아웃 시 503 이 나가고 데이터가 변경되지 않았는지

· T-E: NAS 쓰기 실패 시 로컬 캐시와 미러가 어떻게 남는지

[미검증] T-A~T-E 는 설계만 했고 아직 코드가 없습니다.

v5 에서 코드와 함께 제출하겠습니다. 지금 "테스트를 제출하세요"에

대해 제출할 수 있는 것은 4-1, 4-2 의 실험 하네스뿐입니다.

4-6. 이 항목의 상태

"완전히 해결된다" 표현 안 함 [확인]

/ 다중 프로세스 무력 [확인: 65.6% 손실]

/ 락 없는 RMW 50개 [확인]

/ 일관성 설계 [제안] / 회귀 테스트 [미구현]

5. 임시 파일 교체 — 부분 쓰기와 동시 수정을 분리 평가

귀 지적: "임시 파일 교체는 부분 쓰기와 동시 수정 문제를 구분해서

평가하세요. NAS Rename 의 원자성과 실패 시 기존 파일 보존은

검증 전까지 미검증으로 표시하세요."

두 문제를 분리해서 각각 답합니다. 그리고 두 번째는 "미검증"보다

강한 결론이 나왔습니다.

5-1. 문제 1 — 부분 쓰기 (partial write) [철회]

v3 에서 제가 "전송이 중간에 끊기면 기존 파일이 깨질 수 있다"고

썼습니다. 실측해서 재현되지 않았습니다. 주장을 내립니다.

실험 (2건)

(가) 본문 없이 타임아웃 → 기존 파일 보존 확인

(나) 3,000,678 바이트 멀티파트 본문의 절반만 보내고 소켓 close

→ 기존 27바이트 파일 보존(intact), 신규 파일 생성 안 됨

결과: 두 경우 모두 기존 파일이 그대로였습니다.

→ Synology FileStation Upload 는 본문이 완결되지 않으면 커밋하지

않는 것으로 보입니다. [가정] 서버 구현 내부는 확인할 수 없으므로

이 동작을 "보장"으로 올리지 않고 "관측된 동작"으로만 적습니다.

추가로 단일 프로세스 저장 경로에서 로컬 스토어는 이미

tmp 파일 + os.replace 로 원자적 교체를 합니다. [확인]

즉 로컬 캐시 계층의 부분 쓰기는 방어되어 있습니다.

방어되지 않는 것은 원격 NAS 쓰기인데, 그쪽은 위 실험에서

부분 커밋이 관측되지 않았습니다.

[미검증] 남는 것: NAS 측에서 "부분 업로드가 성공으로 응답되는"

특수한 경우(네트워크가 끊기지 않고 응답만 유실된 경우 등)는

재현하지 못했습니다. 이건 적대적 조건이라 재현이 어렵습니다.

5-2. 문제 2 — 동시 수정 중의 임시 파일 교체 [확인: 불가능]

이게 핵심입니다. 임시 파일에 쓰고 rename 으로 교체하는 전략은

"교체가 원자적"일 때만 성립합니다. 그 전제를 실측했습니다.

실험 결과 (NAS API 직접 호출)

· rename(A → B), B 가 이미 존재

→ {"error":{"code":1200,"errors":[{"code":414,...}]},"success":false}

즉 덮어쓰기를 거부합니다. 코드 414 = 대상 존재.

· move(A → B, overwrite=true)

→ {"error":{"code":102},"success":false}

겹쳐쓰기 이동도 실패합니다.

· rename(A → B), B 가 없음

→ success: true (정상)

결론: 이 NAS 에서는 **temp → 최종이름 rename 으로 원자적 교체가

불가능합니다.** 최종 이름이 존재하는 한 rename 이 거부되기 때문입니다.

원자적 교체를 하려면 존재하는 최종 파일을 먼저 삭제해야 하고,

그러면 "삭제 후 rename" 사이에 파일이 없는 창이 생깁니다.

그 창에서 읽기가 오면 404 또는 빈 값입니다. 즉 원자성을 얻는 대신

가용성 구멍을 만듭니다.

→ 귀 지적은 "검증 전까지 미검증으로 표시하라" 였습니다.

저는 그보다 강한 결론을 제출합니다: 검증 결과 불가능.

"미검증"으로 적으면 나중에 될 수도 있다는 여지를 남기는데,

실제로는 API 가 거부합니다. 불가능으로 적는 편이 정확합니다.

5-3. 그래서 동시 수정은 어떻게 다루나 [제안]

임시 파일 교체로는 못 풉니다. 다른 축으로 갑니다.

· 축 1 — 교체 원자성에 의존하지 않기

파일 하나를 통째로 교체하는 대신, 추가 전용(append-only) 저널을

씁니다. 이벤트를 한 줄씩 덧붙이고, 읽을 때 저널을 재생합니다.

덧붙이기는 rename 이 필요 없습니다. 다만 이건 데이터 구조 변경이라

즉시 적용 대상이 아닙니다. 회원·재정처럼 손실이 치명적인 곳부터

단계적으로 검토할 사안으로 올립니다.

· 축 2 — 쓰기 직렬화(항목 4)로 창 자체를 없애기

동시 수정이 발생하지 않으면 교체 방식의 원자성 문제도 발생하지

않습니다. 즉 항목 4 의 단일 작성자 + 파일 락이 이 항목의

실질적 해법입니다.

· 축 3 — 실패 시 기존 파일 보존은 이미 부분적으로 되어 있음

_save_json 은 쓰기 전에 _safe_snapshot 으로 회전 백업을 남깁니다

(파일당 최근 40개, [확인] 상수 및 디렉터리 확인).

즉 "실패했을 때 되돌릴 수 있는가"에는 이미 답이 있습니다.

8. 캐시 정책 — no-store 기본 · 공개는 명시 분류만 · 기존 사본 처리

귀 지적: "private 캐시는 사용자 계정별 격리를 보장하지 않습니다.

민감 자료의 기본 정책을 no-store 로 두고, 공개 캐시는 명시적으로

전부 동의합니다. 그리고 실측에서 제 코드의 실제 결함을 찾았습니다.

8-1. 신규 결함 F1 — 이미지 응답에 Cache-Control 이 2개 나갑니다 [확인]

실측 (라이브 서버, 이미지 라우트)

GET /api/geo/staticmap?...

응답 헤더에:

Cache-Control: public, max-age=3600, immutable

Cache-Control: no-store

→ 두 개가 동시에 나갑니다. grep -c 로 2 확인.

원인 (소스 확인)

_img_bytes() / _bytes_cache() 는 "public, max-age=..." 를 직접 쓰고,

그 다음 self._cors() 를 호출합니다. 그런데 _cors() 는

모든 응답에 Cache-Control: no-store 를 붙입니다.

_img_bytes 쪽 주석에는 "`no-store` 는 여기서 덮어쓴다

(send_header 는 중복 시 뒤엣것이 이기지 않으므로 _cors() 를

부르지 않고 직접 헤더를 쓴다)" 라고 적혀 있는데,

실제 코드는 self._cors_static() 을 부릅니다(그건 ACAO 만 붙임 → 정상).

그런데 _bytes_cache 는 self._cors() 를 부릅니다 → **no-store 가

추가로 붙습니다.**

왜 이게 위험한가:

· 헤더가 2개면 브라우저·중간 프록시마다 해석이 갈립니다.

RFC 상 중복 Cache-Control 은 "가장 제한적인 것"을 따르는 구현과

"마지막 것"을 따르는 구현이 섞여 있습니다.

· 즉 지금은 정책이 확정되지 않은 상태입니다. 어떤 사용자에게는

public 1시간 캐시가 적용되고, 어떤 경로에서는 no-store 가 이깁니다.

· 이건 "private 이 격리를 보장하지 않는다"는 귀 지적보다 한 단계

앞선 문제입니다. 정책 자체가 모호합니다.

수정 방향:

· 헤더를 쓰는 지점을 한 곳으로 모읍니다. _cors() 는 CORS/보안 헤더만,

캐시 헤더는 별도 함수 하나가 단독으로 결정합니다.

· 중복 Cache-Control 을 금지하는 테스트를 추가합니다

(응답 헤더에서 Cache-Control 개수 == 1 을 강제).

8-2. visibility 기본값 [확인]

귀 지적: "visibility 의 기본값을 public 으로 두지 마세요."

현재 코드 확인 결과:

_cb_visibility(board) 는

· 없으면 openToAll 이 참이면 ALL, 아니면 ADMIN

→ 즉 기본값은 ADMIN(관리자만) 입니다. public 이 아닙니다.

이 항목은 귀 지적과 반대 방향으로 이미 안전합니다. [확인]

다만 별개로 위험한 곳이 있습니다: _default_field_visibility() 입니다.

이건 필드 노출 등급이고, 게시판 visibility 와 다른 개념입니다.

8-3. 실제 캐시 정책의 문제 — 사진은 "공개 자료가 아니다"라고 코드가 말합니다

[확인]

_photo_view_allowed() 의 코드 주석에 이렇게 적혀 있습니다:

"※ 사진은 '공개 자료'가 아니다."

즉 제 코드가 스스로 사진을 비공개로 규정합니다.

그런데 _img_bytes() 는 thumb/mid 에 대해

Cache-Control: public, max-age=2592000 (30일), immutable

을 붙입니다. public 입니다.

이건 귀 지적 8 과 정확히 같은 지점입니다:

· public 은 공유 캐시(중간 프록시, CDN)에 저장될 수 있다는 뜻입니다.

· 사진이 비공개 자료라면 public 이 아니라 no-store 또는 private 입니다.

· private 조차 계정별 격리를 보장하지 않는다는 귀 지적이 맞습니다.

그래서 민감 자료는 no-store 가 기본이어야 합니다.

30일 immutable 도 문제입니다. immutable 은 "이 URL 의 내용은 절대

바뀌지 않는다"는 선언입니다. 사진을 교체하면 URL 의 ?v= 를 바꿔야

무효화된다고 주석에 적혀 있지만, 그 규약이 **클라이언트에 강제되지

않습니다.** 즉 규약을 어기는 경로 하나로 30일간 낡은/잘못된 사본이

남습니다.

8-4. 제안 정책 [제안]

분류를 코드에 명시합니다. 기본값은 안전한 쪽(no-store).

등급 S (민감 — 기본값)

· 회원 개인정보, 사진 원본/파생, 재정, 인가 심사 자료, 후기 본문

· Cache-Control: no-store

· 브라우저 저장 금지. 디스크 캐시 금지.

· 이 등급이 명시 분류가 없을 때의 기본입니다.

등급 P (공개 — 명시 분류한 것만)

· 앱 정적 자산(main.dart.js, 폰트, 아이콘)

· 공개 안내 이미지, 지도 타일(외부 소스)

· Cache-Control: public, max-age=... (불변 자산만 immutable)

· 여기에 넣으려면 코드에서 명시적으로 등급 P 를 지정해야 하고,

지정이 없으면 등급 S 로 처리합니다.

구현 형태:

· 라우트별 캐시 등급을 표로 선언합니다.

CACHE_CLASS = { "/main.dart.js": "P", "/api/photo/...": "S", ... }

표에 없으면 S.

· 응답 헤더는 이 표만 보고 결정합니다. 다른 곳에서 Cache-Control 을

쓰지 못하게 합니다(중복 방지 = 8-1 수정).

· 테스트: 모든 라우트에 대해 Cache-Control 이 정확히 1개인지,

등급 S 라우트가 no-store 인지 검사.

8-5. 기존에 저장된 캐시 사본 처리 [확인 + 제안]

귀 지적: "기존에 저장된 캐시 사본의 처리도 검토하세요."

서버 측에 이미 쌓여 있는 사본 (실측)

.static_compress_cache 1.1G (정적 자산 압축본 — 공개 자산이라 위험 낮음)

    .thumb_cache             127M   (사진 썸네일 — 민감)
    .media_cache             110M   (영상/큰 이미지 — 민감)
    .json_mirror             8.3M   (업무 JSON 원문 — 민감)
    .ev_meta_cache           2.9M   (행사 메타 — 민감)
    gdrive_store             3.0G   (항목 9 참조)
    .safe_snapshots          334M   (쓰기 직전 원문 — 민감)

이건 "브라우저 캐시"가 아니라 서버 디스크 사본입니다.

브라우저 쪽 기존 사본은 서버가 지울 수 없습니다(이미 사용자 기기에

있음). 그래서 두 문제를 나눠 다룹니다.

(가) 브라우저에 이미 저장된 사본

· 서버가 할 수 있는 일: URL 을 바꿔 무효화(?v= 갱신),

또는 응답 헤더를 no-store 로 바꿔 앞으로를 막는 것.

· 이미 저장된 것은 만료 전까지 남습니다. 이건 피할 수 없습니다.

· 정확한 서술: "기존 사본은 만료 시까지 남는다. 즉시 삭제는

기술적으로 불가능하다." 이 한계를 명시해야 합니다.

· 완화: 민감 등급은 max-age 를 0/no-store 로 바꾸고,

사진 URL 에 사용자 세션 종속 토큰을 붙여 재사용을 어렵게 합니다.

(나) 서버 디스크 사본

· 이것들은 우리가 지울 수 있습니다.

· 제안: 등급 S 에 해당하는 디렉터리(.thumb_cache, .media_cache,

.json_mirror, .ev_meta_cache, .safe_snapshots)는

"캐시"가 아니라 로컬 사본으로 재분류하고,

보관 정책(보관 기간·상한·암호화 여부)을 명시합니다.

· 즉시 삭제는 하지 않습니다. 이유: 이걸 지우면 NAS 왕복이 늘어나

성능이 떨어지고, NAS 장애 시 가용성이 사라집니다(현재 구조가

이 사본에 의존). 정책을 정한 뒤 단계적으로 줄이는 것이 맞습니다.

8-6. 이 항목의 상태

visibility 기본값이 이미 public 아님 [확인]

/ Cache-Control 중복 = 정책 모호 [확인: 신규 결함 F1]

/ 사진을 public 으로 캐시하는 모순 [확인: 결함]

/ no-store 기본 + 명시 분류 [제안]

/ 기존 브라우저 사본 즉시 삭제 불가 [확인]

/ 서버 디스크 사본 정책 [제안, 삭제 안 함]

9. gdrive_store — 역할 미확정으로 표시, 삭제하지 않음

귀 지적: "gdrive_store 는 영구/캐시 분류가 문서 안에서 불일치합니다.

확인 전 삭제하지 말고 역할 미확정으로 표시하세요. 미디어 원본과

수정 가능한 업무 JSON 의 정책을 구분하세요."

9-1. 문서 안 불일치를 확인했습니다 [확인]

같은 디렉터리를 코드 주석이 두 가지로 부릅니다:

_install_backend() 안, mode="nas" 분기:

"NAS(read-through cache) + store"

→ 읽기 통과 캐시

_LocalStore 클래스 docstring:

"로컬 디스크 스토어 — 백엔드 무관한 빠른 캐시/이중화(RAID) 계층.

… 나중에 이 저장소를 주 저장소로 승격하면 그대로 0ms 백엔드다."

→ 캐시이자 이중화(백업)이자 잠재적 주 저장소

_BackendClient docstring:

      mode="nas"    : 로컬 스토어 = 읽기 통과 캐시
      mode="gdrive" : 로컬 스토어 = **주 저장소**

즉 한 디렉터리가 "캐시"이면서 동시에 "이중화본"이고, 백엔드 모드에

따라 "주 저장소"가 됩니다. 이게 귀 지적의 불일치입니다. 맞습니다.

9-2. 왜 이게 위험한가 — 잘못 지우면 복구 불가 [확인]

· NAS 모드에서 쓰기는 "로컬 + NAS 동시 기록(무손실)"입니다.

[확인] 코드 주석과 구현 모두 그렇게 되어 있습니다.

즉 로컬 사본이 NAS 실패 시의 유일한 사본일 수 있습니다.

· "캐시니까 지워도 된다"고 판단해서 지우면, 그 순간 NAS 에도

반영되지 않은 값이 있었다면 복구 불가입니다.

· 실제로 _BackendClient.write 는 NAS 쓰기 예외를 삼키고 성공을

반환합니다(5-3 참조). 즉 "NAS 에도 있다"고 확신할 수 없는 상태가

만들어질 수 있습니다.

→ 그러므로 삭제 금지. 역할 미확정으로 표시합니다.

9-3. 실측 — 무엇이 들어 있는가 [확인]

3,001.8 MB / 1,501개 blob. 내용 분류(매직바이트 + JSON 파싱):

    jpeg          1,181개
    json(유효)      259개     1,795,268,775 B (약 1.71 GB)
    other/binary     20개
    png              18개
    mp4/mov          15개
    webp              8개

주목할 점:

· JSON 이 용량의 대부분(1.71GB / 3.0GB) 입니다. 캐시라기보다

업무 데이터 사본에 가깝습니다.

· 가장 큰 JSON 3개가 각각 약 7.95MB 로 거의 같습니다

(7954568 / 7954153 / 7954046). 같은 데이터의 세대별 사본으로

보입니다. [가정] — 키를 복원해 확인하지 못했습니다.

· 24MB 초과 blob 은 0개. max_blob(24MB 기본)이 실제로 동작해서

큰 영상은 저장되지 않았습니다.

· 즉 "영상 원본이 여기 쌓여 있다"는 추측은 사실이 아닙니다.

영상은 .media_cache(110M) 쪽입니다.

9-4. 미디어 원본과 업무 JSON 의 정책을 구분 [제안]

두 종류는 성질이 다릅니다. 같은 정책을 쓰면 둘 다 잘못됩니다.

(가) 미디어 원본 (jpeg/png/webp/mp4 — 여기서는 1,222개)

· 성질: 불변. 한 번 만들어진 사진/영상은 내용이 바뀌지 않습니다.

(교체는 "다른 파일"이지 "같은 파일의 수정"이 아님)

· 그래서 캐시로 취급해도 안전합니다. 지워도 NAS 에서 다시 받습니다.

· 정책 제안:

- 불변 자료로 분류. 캐시 삭제 허용.

- 단, NAS 원본 존재를 확인한 뒤에만 삭제.

(확인 없이 지우면 9-2 의 위험)

- 상한·LRU 는 이미 있음. 유지.

(나) 수정 가능한 업무 JSON (259개)

· 성질: 가변. 같은 경로의 내용이 계속 바뀝니다.

즉 "캐시"가 아니라 사본입니다.

· 손실이 곧 업무 데이터 손실입니다. 회원·재정·심사가 여기 있습니다.

· 정책 제안:

- 캐시로 분류하지 않습니다. 사본( replica ) 으로 분류.

- 삭제 금지. 보관 기간·세대 수를 명시.

- NAS 와의 일치 여부를 확인하는 검사를 둡니다

(해시 비교, 불일치 시 경고만 하고 자동 삭제하지 않음).

- 항목 4 의 쓰기 직렬화 대상과 같은 목록입니다.

- 백업 정책에 포함합니다(현재 백업 대상인지 확인 필요 [미검증]).

(다) 판정 불가 (other/binary 20개)

· 매직바이트로 분류되지 않았습니다. 삭제 대상이 아닙니다.

· 역할 미확정으로 표시하고 보존합니다.

9-5. 역할 미확정 표시 [확인]

이 문서와 코드 주석에서 gdrive_store 의 역할을 이렇게 고정합니다:

"역할 미확정 (캐시 / 이중화 / 주 저장소 후보가 혼재).

확인 전 삭제 금지.

미디어 blob 은 불변 캐시로 볼 근거가 있으나 NAS 원본 확인 전

삭제 금지. JSON blob 은 가변 사본으로 보아 삭제 금지."

코드 주석도 이에 맞춰 고칠 것을 제안합니다

(현재는 "캐시/이중화"로 단정하고 "주 저장소로 승격"까지 언급).

[제안] 이번 턴에서는 코드를 고치지 않았습니다. 승인 없이 운영 코드를

바꾸지 않는다는 원칙을 지켰습니다.

10. SSH 터널 조건 · TLS 인증서 검증 — 현재 코드가 이미 위반 중입니다

귀 지적: "SSH 터널 사용 시 loopback 바인딩·키·포워딩 제한과 TLS

호스트명 검증을 유지하세요. 인증서 검증 해제는 금지합니다."

이 항목에서 제 코드가 이미 금지 사항을 위반하고 있습니다.

가장 무거운 보고입니다.

10-1. 신규 결함 F2 — TLS 검증이 해제되어 있습니다 [확인]

nas_lib.py, 클래스 NasClient 생성자:

self.ctx = ssl.create_default_context()

self.ctx.check_hostname = False

self.ctx.verify_mode = ssl.CERT_NONE

즉 프록시는 NAS 에 HTTPS 로 붙지만, 인증서를 전혀 검증하지 않습니다.

호스트명도 확인하지 않습니다.

→ 중간자가 인증서를 아무거나 내밀어도 프록시는 그대로 통신합니다.

→ "TLS 를 쓴다"는 사실만으로는 아무것도 보호되지 않습니다.

왜 이렇게 되어 있는지 (제가 짠 코드의 사정):

NAS 인증서가 자체서명입니다. 실측한 인증서 정보:

CN = synology, SAN = DNS:synology

O = Synology Inc., L = Taipel, C = TW

notBefore 2026-05-01 11:51:43 GMT

notAfter 2027-05-02 11:51:43 GMT

접속 주소는 https://<NAS-IP>:5001 입니다.

호스트명(NAS 의 IP)과 인증서 SAN(synology)이 애초에 불일치입니다.

그래서 검증을 켜면 즉시 실패하고, 그걸 피하려고 껐습니다.

즉 설계 결함이 아니라 회피입니다. 인정합니다.

그리고 이건 귀 지적 10 의 "인증서 검증 해제는 금지"에 정면으로

위배됩니다. 이 상태로는 safe_to_set_hub_live 를 true 로 올릴 수

없다고 저도 봅니다.

10-2. 고치는 방법 — 세 가지, 각각 조건이 다름 [제안]

(가) NAS 에 정식 인증서를 넣고 IP 대신 호스트명으로 접속

· 조건: 도메인(또는 내부 DNS 이름) + 유효 인증서 + 그 이름으로

접속. NAS 가 Synology 이므로 Let's Encrypt 적용이 가능합니다.

· 결과: 검증을 정상적으로 켤 수 있습니다. 가장 깔끔합니다.

· 제약: 이건 NAS 관리자 작업입니다. 제가 샌드박스에서 못 합니다.

(나) 자체서명 인증서를 고정(pin) 하고 검증 유지

· 인증서 지문을 코드에 고정하고, 연결 시 지문을 비교합니다.

· ssl.CERT_NONE 이 아니라, 커스텀 검증으로 지문 일치를 강제합니다.

(검증을 끄는 것과 다릅니다. 특정 인증서만 허용하는 것입니다.)

· 조건: 인증서 교체 시 코드도 갱신해야 합니다. 만료 2027-05-02

전에 갱신 절차가 필요합니다.

· 장점: 지금 당장 할 수 있습니다. NAS 관리자 작업 불필요.

· 단점: 인증서에 NAS 의 신원 정보가 약합니다(SAN=synology).

즉 호스트명 검증을 하는 것이 아니라 "이 인증서와 대화 중"만

보장합니다. 중간자 방지는 되지만 신원 확인은 약합니다.

(다) 사설 CA 를 만들고 그 CA 를 신뢰

· 자체서명 대신 사내 CA 로 서명하고, 프록시는 그 CA 만 신뢰.

· 호스트명 검증까지 정상 동작하게 하려면 SAN 에 접속 이름을 넣어야

합니다. 즉 (가)와 같은 조건이 필요합니다.

[제안] 단계는 이렇게:

1단계(즉시): (나) 지문 고정으로 CERT_NONE 을 제거.

→ "검증 해제" 위반을 즉시 해소. 신원 확인은 약하지만

무검증보다는 엄격히 낫습니다.

2단계(도메인 확보 후): (가) 정식 인증서 + 호스트명 검증.

→ 완전한 형태.

[미검증] 어느 쪽을 택할지는 소유자·NAS 관리자 결정입니다.

제가 임의로 (나)를 적용하지 않았습니다. 운영 코드 변경이기 때문입니다.

10-3. SSH 터널 조건 [제안]

현재 저장소에 SSH 사용 흔적은 deploy/deploy.sh 의 ssh 호출뿐이고,

NAS 접속에는 터널을 쓰지 않습니다(직접 5001 접속). [확인]

그래도 귀 지적대로 조건을 명시합니다.

· loopback 바인딩: 터널은 반드시 127.0.0.1 에만 바인딩.

0.0.0.0 에 열면 같은 호스트의 다른 사용자가 터널을 탈 수 있습니다.

예: ssh -N -L 127.0.0.1:15001:내부NAS:5001 ...

("-L 15001:..." 처럼 호스트 부분을 생략하면 기본이 loopback 이지만,

명시적으로 적는 편이 안전합니다.)

· 키: 전용 키를 만들고 passphrase 를 둡니다. root 공용 키 재사용 금지.

authorized_keys 에는 from=, command=, restrict 로 제한합니다.

· 포워딩 제한: 서버 측 sshd 에서 AllowTcpForwarding 을 필요한 방향만

허용. 사용자가 임의 포워딩을 열지 못하게 합니다.

· TLS 호스트명 검증 유지: 터널을 쓴다고 TLS 검증을 끄면 안 됩니다.

터널은 구간을 암호화할 뿐, 종단 인증서 검증을 대체하지 않습니다.

터널 + CERT_NONE 조합은 여전히 무검증입니다.
